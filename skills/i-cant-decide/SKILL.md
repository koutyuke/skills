# I Can't Decide

ユーザーはよく知らない分野の選択肢を前にして、1 つに決められずにいる。このスキルでは、Agent が代わりに選択肢を洗い出し、調べて比較し、推奨度（⭐1〜5）とその理由を返す。

目指すのは網羅的な比較表を作ることではなく、ユーザーが結論の行だけ読んでも次に何をすればよいか分かり、理由を読めば納得できる回答である。

## 推奨度の基準

推奨度は今回の目的と条件に照らして判定する。⭐5 は「今回の候補の中で一番良い」ではなく、「これを選べば間違いない」という意味を表す。候補がどれも今ひとつなら、すべて ⭐1〜2 でよい。一番良い案を ⭐5 に引き上げることはしない。

| 推奨度     | 意味                     | 当てはまる状態                                                                                                                                 |
| ---------- | ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| ⭐⭐⭐⭐⭐ | 迷わず選んでよい         | 必須条件をすべて満たすことを根拠つきで確認できた。今回の状況で困る欠点がなく、実績があり、つまずきやすい点も分かっている。明らかに上の案がない |
| ⭐⭐⭐⭐   | 選んでよい。注意点がある | 必須条件を満たす。欠点や手間はあるが、今回の状況では受け入れられ、対処法も分かっている。または、明らかに上の案がある                           |
| ⭐⭐⭐     | 条件次第                 | 合うかどうかがまだ確認できていない事実か、ユーザーにまだ聞けていない好み・優先順位で決まる。その条件が満たされれば ⭐4 以上になる              |
| ⭐⭐       | おすすめしない           | 必須条件は満たすが、今回の状況では受け入れにくい大きな欠点がある                                                                               |
| ⭐         | 選ばない                 | 必須条件を満たさない、または致命的な問題がある（保守の終了、未対応のセキュリティ上の欠陥、目的に合わない、予算や期限を超える）                 |

- **必須条件**: 依頼の文面、プロジェクトの現状（使っている言語や基盤、規約）、ユーザーが述べた予算・期限などから読み取る。
- **明らかに上の案**: 採用でき、重要な点でどれも劣らず、少なくとも 1 つの点ではっきり勝る案。

推奨度は次の問いを上から順に当てはめ、最初に「はい」になった段階とする。問い 1・2 は確認できた事実だけで判定する。欠点が今回の状況で問題になるかが分からなければ、問い 3 に進む。

1. 必須条件を満たさない、または致命的な問題があるか → ⭐1
2. 今回の状況では受け入れにくい大きな欠点があるか → ⭐2
3. 合うかどうかがまだ確認できていない条件で決まるか → ⭐3
4. 注意点はあるが受け入れられ、対処法も分かっているか。または明らかに上の案があるか → ⭐4
5. ⭐5 の「当てはまる状態」をすべて根拠つきで確認できたか → ⭐5。確認できないものがあれば ⭐3 に戻す

## 1. 選択肢を洗い出す

- 依頼文、会話、関係するソースコード・設定・文書から、ユーザーが挙げた選択肢を拾う。「X でいい？」のように 1 つしか挙がっていなければ、それも候補として扱う。
- 選ぶ目的と必須条件もここで読み取る。分からない条件はまず自分で調べる。調べても分からない条件のうち、答えによって結論が変わるものだけをユーザーに聞く。それ以外は仮定を置いて進め、回答に記載する。
- 依頼されていなくても、Agent も選択肢を考える（「2. Agent の案を考える」を参照）。「ほかにいい案はある？」と聞かれたときは特に念入りに考える。

ユーザーはその分野に詳しくないため、答えやすい形式で質問する。

- 一度に聞くのは 3 問までとする。ある答えによって次に聞くことが変わるなら、分けて聞く。追加で聞くのは、まだ結論を変える条件が残っているときだけとする。
- 選択式の質問ツール（`AskUserQuestion`、`request_user_input` など）が使えれば、そのツールを使って質問する。
- 選択肢は、ユーザーが自分の状況として答えられる言葉で書く（「利用者は 100 人以下」「月 1 万円まで」）。専門用語を選択肢にしない。
- 「分からない」も選べるようにする。分からない、無回答、タイムアウトだった条件は、確認できたことにしない。仮定を置いて進め、その条件で合うかが決まる案は ⭐3 にする。

## 2. Agent の案を考える

ユーザーの前提から仮定を立て、その仮定から案を作る。数合わせで案を増やさない。

1. **前提を読む**: 目的と制約（予算、期限、規模、既存の技術、ユーザーの経験）を、依頼とプロジェクトから読み取る。
2. **ある世界を考える**: 検討している手段を使った世界を思い描く。何が良くなり、何が悪くなり、今と何が違うか。
3. **ない世界を考える**: その手段を使わない世界で、何が不便で、何は特に困らないか。今すでに別の手段を使っているなら、それを使い続ける世界を考える。候補がまだ 1 つもなければ、困りごとが解消した世界と、今のやり方を続ける世界を比べる。どちらの世界も、同じ利用場面・期間・規模で考える。
4. **仮定を置く**: 2 つの世界の差から、「ユーザーが得たい効果は E。制約 C の下で」という仮定を置く。目的が明示されていれば、それをそのまま E にする。仮定で補うのは、明示されていない部分だけとする。
5. **案を作る**: E を別の方法で得られる案を考える。

例: 「導入すれば手作業の転記がなくなる。導入しなければ月 2 時間の転記が続く」→ 得たい効果は転記の削減 → 別の製品に加え、今あるツールの機能で自動化する案も候補にする。

案は、たとえば次の方向から作る。

- 同じ効果を得られる別の手段・製品・方式
- 今あるもの（プロジェクト内の仕組み、導入済みのツール）で済ませる
- ユーザーの案同士の組み合わせ、または小さく試してから決める段階導入
- やらない、または現状維持。ない世界でも特に困らないなら有力な候補となる

置いた仮定は回答に記載する。仮定が外れていた場合に、ユーザーが訂正して選び直せるようにするためである。

## 3. 調べる

各選択肢の良い点と悪い点を、推奨度と結論を左右するところまで徹底的に調べる。

- **プロジェクト内**: ソースコード、設定、依存のバージョン、README や ADR などの文書。既存の構成や規約に合うか、導入・移行にどれだけ手間がかかるかを確かめる。
- **一次情報**: 公式ドキュメント、仕様、リリースノート、価格表、ライセンス。保守が続いているか（最終リリース、Issue への対応）も確認する。
- **一般論と評判**: 事実上の標準や一般的な推奨、実際に使った人の経験談、比較記事、フォーラムや Issue での議論。どれが広く選ばれているか、どこでつまずきやすいかは、一次情報だけでは分からない。1 つの意見に頼らず、独立した複数の情報源で傾向を確かめる。書き手の立場（開発元、競合、宣伝）、時期、前提の規模や用途が今回の状況に当てはまるものだけを根拠にする。

調べた内容は、事実（一次情報やコードで確認したこと）、評判、Agent の推論、未確認を区別しておく。コードは実物で、仕様と価格は公式の一次情報で確かめる。時期で変わる情報（価格、保守状況、対応バージョン）には確認日を添える。残る不明が結論を変えないか、調査では解けず確かめ方が決まったら、調査を終える。

調べたあと、良い点と悪い点を要約する。

- ユーザーにとって何が起きるかで書く。「コストが高い」より「利用者 1,000 人で月 2 万円かかる」と書く。
- 意味を落とさない。数値や「〜の場合は」という条件は残す。
- 専門用語は初出で一言の説明を添えるか、平易な言葉に置き換える。
- 全案に共通する良い点・悪い点は、案ごとに繰り返さない。

## 4. 評価して比べる

- **単体で評価する**: 各案を「推奨度の基準」の問いに当てはめ、仮の推奨度を付ける。
- **ほかの案と比べる**: 案同士の差が出るところで比べ、明らかに上の案があるかを判定して、仮の推奨度を見直す。同じ推奨度の案が複数あれば、決め手（既存の構成との相性、事実上の標準か、手間の少なさなど）で 1 つに絞る。
- 推奨度の理由は、どの問いで決まったかで説明できるようにする。⭐3 なら、何が分かれば何段階になるかも書けるようにする。

結論では、ユーザーが次にすることを 1 つに絞って示す。ユーザーは選べないから頼んでいるので、「どれも一長一短」で終わらせない。推奨する案は、回答に載せる案（「5. 回答する」を参照）から選ぶ。

| 最高評価 | 結論                                                                                                                                                    |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ⭐4〜5   | その案を推奨する                                                                                                                                        |
| ⭐3      | まず確かめることを 1 つ示し、その確かめ方と、結果ごとにどの案を選ぶかを書く（「X なら A、そうでなければ B」）                                           |
| ⭐1〜2   | 勧められる案がないと伝え、見直す条件や別の方向を示す。挙がった案から選ぶしかないとユーザーが示していれば、⭐2 の案から 1 つを、欠点への備えと一緒に示す |

## 5. 回答する

回答に掲載する案は次のとおりとする。

- ユーザーが挙げた案は、評価にかかわらずすべて載せる。
- Agent の案は、ユーザーの案の最高評価より高い推奨度のものだけ載せる。それ以下の案は不要な情報となるため載せない。
- ただし、ユーザーが Agent の案を求めた（「ほかにいい案はある？」など）場合は、最高評価と同じ推奨度の案も載せる。
- ユーザーが案を 1 つも挙げなかった場合は、⭐3 以上の Agent の案を載せる。⭐3 以上がなければ、最も評価の高い案を載せる。
- Agent の案には、案名の後ろに「（Agent 案）」と付ける。

次の形式で書く。

```markdown
**結論: <案名> を推奨** ⭐⭐⭐⭐⭐
<決め手を 1〜2 文>
<結論を左右する仮定があれば: 「<仮定> を前提にしています。違う場合は <どう変わるか>」>

| 推奨度     | 案                 | ひとことで         |
| ---------- | ------------------ | ------------------ |
| ⭐⭐⭐⭐⭐ | <案名>（Agent 案） | <選ぶ理由を一言>   |
| ⭐⭐⭐⭐   | <案名>             | <注意点を一言>     |
| ⭐⭐       | <案名>             | <避ける理由を一言> |

### <案名>（Agent 案） ⭐⭐⭐⭐⭐ 迷わず選んでよい

- 良い点: <ユーザーにとって何が起きるか>
- 悪い点: <同上>
- 評価の理由: <どの問いでこの段階になったか。⭐3 なら、何が分かれば何段階になるか>

（表の順に、ほかの案も同じ形で書く）

**出典**: [<情報源の名前>](URL)（確認日 YYYY-MM-DD）
```

- 結論の行は、最高評価に応じて「<案名> を推奨」「まず <確かめること> を確認」「勧められる案はありません」を使い分ける。星は案を推奨するときだけ付ける。
- 表と各案の説明は、推奨度の高い順に並べる。
- 星の数は推奨度と同じにし、空の星（☆）は付けない。各案の見出しには、星の後ろに「推奨度の基準」の「意味」を添える。
- 良い点・悪い点は、該当するものを各 3 個まで書く。ない場合は書かない。評判に基づく点は、「利用者の声では」のように事実と区別して書く。
- 仮定と出典は、該当がなければ省く。出典には、実際に参照した情報源だけを書く。
- 比較だけを頼まれた場合は、推奨を示して終える。実装などの続きの作業も頼まれている場合は、その依頼の範囲で推奨の案を使って進める。ただし、どの案を選ぶかで作業の範囲や影響が大きく変わるなら、着手前にユーザーに確認する。
