# Twintail

> Carve away everything the change doesn't need.

削る対象は今回の変更であって、既存のコードベースではない。頼まれていない既存コードの削除やリファクタリングは、このスキルの目的に含まれない。

目的は、要件を満たす変更のうち、読む人と保守する人の負担が最も小さいものを選ぶこと。行数を減らすこと自体は目的ではない。

書いたコードは、読まれ、テストされ、移行され、障害時に誰かが追いかける対象になる。だから「どう書くか」の前に「書かずに済む方法はないか」を探す。

## 1. 小さくする前に理解する

最小化は理解の後に行う。理解を省いた小さな差分は、自信ありげな誤修正になりやすく、最も危険。

- 依頼が症状を述べているのか、原因を述べているのかを見分ける
- 変更が通る実際の処理の流れを、入口から出口までたどる
- 触る関数・型・設定の呼び出し元を洗い出す（`grep`、参照検索）
- 周辺のコードがどんな設計パターンと規約で書かれているかを見る

小さい差分でも、場所が間違っていれば 2 つ目のバグになる。

## 2. 手段は上から順に検討する

上から順に検討し、成立した最初の段で止まる。深く調べ込む手順ではなく、理解した後に素早く当てはめる判断順。

1. **作らない**: 今の要件に本当に必要か。「将来使うかもしれない」は理由にならない。不要なら一文でそう伝える
2. **リポジトリ内の既存資産を使う**: ヘルパー、型、共通コンポーネント、既存のパターン。近くのファイルに同じものがあるのに書き直すのが、最もよくある無駄
3. **言語と標準ライブラリを使う**
4. **プラットフォームや基盤の機能を使う**: HTML/CSS の標準機能、DB の制約、フレームワークの既存機構、設定での対応
5. **導入済みの依存を使う**
6. **最小の実装を新しく書く**

新しい依存の追加は最後の手段にする。追加するなら、用途・代替案・影響範囲・ロックファイル更新の有無を報告する。

同じくらいの大きさの選択肢が 2 つあるなら、境界条件で正しく動く方を選ぶ。コードを短くするために、誤りうるアルゴリズムを選ばない。

## 3. バグは共通の原因箇所で直す

報告されるのは症状で、同じ原因を共有する別の経路が壊れたまま残っていることが多い。共通の関数を 1 か所直すほうが、呼び出し元ごとにガードを足すより差分が小さく、直し漏れもない。

ただし共通箇所を変えると、ほかの呼び出し元の挙動も変わる。手順 1 で洗い出した呼び出し元それぞれで、変更後の挙動が正しいかを確かめる。

## 4. 書かないもの

| 避けるもの                                      | 代わりに             | 書いてよい条件                                               |
| ----------------------------------------------- | -------------------- | ------------------------------------------------------------ |
| 実装が 1 つしかないインターフェースや抽象クラス | 具象クラス           | 2 つ目の実装が今必要、またはプロジェクトの慣習がそうしている |
| 1 種類しか作らないファクトリやビルダー          | コンストラクタや関数 | 生成手順が実際に複雑                                         |
| 変わらない値の設定化・引数化                    | 定数                 | 環境や利用者ごとに値が実際に違う                             |
| 「後で使う」ための雛形や空の拡張点              | 書かない             | ―                                                            |
| 呼び出し元が 1 つしかない汎用ユーティリティ     | その場に書く         | 同じ処理が 3 か所目に現れた                                  |
| 中継するだけの薄いラッパー層                    | 直接呼ぶ             | 境界を隔離する明確な理由がある                               |
| 起こりえない状態への防御コード                  | 型や前提で排除する   | 信頼境界の外から入力が来る                                   |
| 数行で書ける処理のための新しい依存              | 数行のコード         | 標準化された難しい処理（暗号、日付計算など）                 |
| ついでのリネームや整形                          | 触らない             | 依頼の範囲に含まれている                                     |

プロジェクトの規約や既存の設計が層や抽象を求めているなら、それに従う。周囲と違う書き方をした「最小」は、読み手にとって最小ではない。一貫性はこのスキルより優先する。

## 5. 削ってはいけないもの

次のものは、差分が大きくなっても省かない。

- ユーザーが明示的に求めたもの
- 信頼境界での入力検証、認証・認可、秘密情報の扱い
- データの損失や不整合を防ぐエラー処理やトランザクション
- アクセシビリティの基本
- プロジェクトの運用が前提としているログや監視
- 実環境のばらつきに合わせるための調整値（タイムアウト、リトライ回数、しきい値など）

**テストについて**: 最小化の対象は本番コードであり、テストは減らす対象ではない。テストはグローバルの開発方針（TDD）とプロジェクトのテスト戦略に従う。そのうえで、テストも「壊れたら落ちる最小のケース」に絞り、同じことを確かめる重複ケースは足さない。

## 6. 近道を選んだら限界を書く

既知の上限がある単純化を意図的に選んだら、その限界と切り替える条件をコメントに残す。対象は、全体ロック、O(n²) の走査、単純なヒューリスティクス、固定値でのハードコードなど。

```java
// 全件を走査している。件数が数万を超えるようならインデックス付きの検索に切り替える
```

コメントの言語や形式はプロジェクトの規約に合わせる。独自のマーカーは作らない。既存の `TODO` の運用があれば、それに従う。

## 7. 依頼が大きすぎると感じたとき

| 状況                                           | 対応                                                                   |
| ---------------------------------------------- | ---------------------------------------------------------------------- |
| もっと小さい方法で、依頼の目的を満たせる       | 小さい方法で実装する。省いたものと、それが必要になる条件を一文で添える |
| 小さい方法では、明示された要件を満たせない     | 要件どおりに作る。より簡単な代替案は一文で提案するだけにする           |
| どちらが要件なのか判断できず、後から戻しにくい | 実装前に質問する                                                       |

ユーザーが完全版を求めたら、蒸し返さずに作る。

## 8. 完了前に差分を見直す

完了と言う前に `git diff` を読み、次を確かめる。

- 各変更について、それを消したら何のテストや要件が壊れるか。答えられない変更は消す
- 同じことをする既存コードがないか
- 今回自分で足したのに、使われなくなったコード、import、引数、ファイルが残っていないか
- 依頼と無関係な変更が混ざっていないか

同じ種類の過剰設計が繰り返し見つかるなら、プロンプトではなく、リンターや `ast-grep` のルールで防ぐことを提案する。

## 9. 説明も最小十分にする

単純化を弁護する長い説明は、複雑さを文章に移しただけ。

- 最終報告は、グローバルの完了条件の形式（変更点・検証結果・未検証事項・残リスク）に従い、各項目を短く書く
- 省いたものは「省いたもの: X。Y になったら追加する」と一文で書く
- ユーザーが明示的に求めた説明（調査報告、設計の解説、手順の説明）は省略しない

## 10. レビューで使うとき

過剰設計の指摘は、削除や置き換えを具体的に書けるものに限る。

- 形式: `ファイル:行` — 何を消すか、何に置き換えるか — 理由（1 行）
- 正しさのバグの指摘とは分けて書く
- プロジェクトの規約に沿った構造は、指摘の対象にしない
- 「もっと汎用的にすべき」という方向の指摘は、このスキルの対象外

## 例

**依頼**: 「一覧 API のレスポンスをキャッシュしたい」

- まず確認すること: キャッシュが必要なほど遅いのか。リポジトリに既存のキャッシュ機構（Spring の `@Cacheable`、共通のキャッシュユーティリティなど）はないか
- 既存の機構があれば、それを付けるだけにする。無効化の条件は、既存の同種の実装に合わせる
- 報告: 「既存の `XxxCache` を利用した。独自のキャッシュクラスは省いた。TTL を個別に制御したくなったら追加する」

**依頼**: 「日付入力のために date picker ライブラリを入れて」

- まず確認すること: デザインシステムや既存のコンポーネントに日付入力があるか。なければ `<input type="date">` で要件を満たせるか
- 既存のコンポーネントで満たせるなら、それを使い、ライブラリは入れない。ライブラリが必要な要件（範囲選択、祝日の表示など）が明示されているなら、要件どおりに入れる
