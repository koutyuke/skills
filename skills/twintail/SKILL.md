# Twintail

要件を満たす変更のうち、読む人と保守する人の負担が最も小さいものを選ぶ。行数やファイル数の少なさは目的ではない。

対象は今回の変更で、頼まれていない既存コードの削除や整理はしない。

## 1. 先に固定する条件

小さくする前に、次を満たすことを決める。満たさない案は、どれだけ小さくても選ばない。

- 明示された要件と、ユーザーが指定した手段
- 境界条件を含む正しさと、変更を頼まれていない既存の契約（公開 API、入出力、エラー時の挙動、保存データの形式）
- 信頼境界での入力検証、認証・認可、秘密情報の扱い、データの損失を防ぐ処理
- プロジェクトの規約と既存の設計（層の分け方、命名、テストの書き方）
- アクセシビリティの基本と、運用や監査が前提にしているログや監視

## 2. 理解してから選ぶ

1. 依頼が症状を述べているのか原因を述べているのかを見分け、変更する箇所の責務と、そこを通る処理の流れを読む。
2. 変更する関数・型・設定の利用先を検索する。影響を説明でき、検証方法を選べるところまで調べたら止める。共有される箇所や、失敗の影響が大きい変更ほど広く調べる。
3. 手段は上から順に探し、「先に固定する条件」をすべて満たす候補が見つかった段で止める。
   1. 作らずに済む（今の要件に必要ない）
   2. リポジトリ内の既存のヘルパー・型・部品・パターンを使う
   3. 言語と標準ライブラリを使う
   4. プラットフォームやフレームワークの機能を使う（HTML/CSS、DB の制約、フレームワークの仕組み、設定）
   5. 導入済みの依存を使う
   6. 新しいコードを書く。新しい依存は最後
4. 既存のヘルパーを使うためにモード引数・変換・分岐を足す必要があるなら、無理に使い回さず次の段と比べる。

## 3. 足す前に問う

新しい関数・クラス・設定・依存・防御コード・テスト・コメントは、今回の要件・正しさ・規約・安全性のどれに必要かを言えるものだけ足す。「将来使うかもしれない」は理由にならない。

| よくある過剰 | 代わりに | 足してよい条件 |
| --- | --- | --- |
| 実装が 1 つのインターフェース、1 種類しか作らないファクトリ | 具象クラスや関数を直接使う | 2 つ目の実装が今要る、外部依存を隔離する境界になる、規約がそうしている |
| 変わらない値の設定項目・引数・環境変数 | 定数 | 環境や利用者ごとに値が実際に違う |
| 使われない汎用ユーティリティ、「後で使う」雛形や拡張点 | 書かない | ― |
| 中継するだけの層やラッパー | 直接呼ぶ | 外部の型や仕様が内部へ広がるのを止めている |
| 内部で保証済みの値への重複チェック | 型や前提で排除する | 信頼境界の外から来る値 |
| 失敗を隠す catch や既定値 | 失敗はそのまま伝える | 実際に復旧できる、契約に沿ってエラーを変換する、秘密情報を伏せる、後片付けをする |
| 数行で書ける処理のための新しい依存 | 標準ライブラリか数行のコード | 暗号、日付・タイムゾーン、構文解析など、正しく書くのが難しい処理 |
| 頼まれていないキャッシュ・並列化・リトライ・ログ | 書かない | 要件や計測で必要と分かっている、運用・監査の規約が求めている |
| ついでのリネーム・整形・リファクタリング | 触らない | 依頼に含まれている |
| 頼まれていない README やドキュメントの追記 | 書かない | 既存の記述が今回の変更で事実と食い違う、同種のもの（API・設定・コマンドの一覧など）をすでに文書化している、利用者が設定する値（環境変数など）を新しく加えた |

表の条件は判断の目安で、回数や行数の閾値ではない。名前で意図を示すための関数抽出や、同じ業務ルールの重複の集約は、呼び出し元が 1 つでもよい。

後から変えにくい決定（公開 API、保存データの形式、権限の境界）は、将来の機能を作らない場合でも、今の要件で何を約束するかを確かめる。

## 4. 場面ごとの注意

**バグ修正**: 症状から原因までたどり、原因に責任を持つ箇所で直す。報告された経路にだけガードを足すと、同じ原因を持つ別の経路が壊れたまま残る。

- 共有の関数を直したら、利用先ごとに変更後の挙動を確かめる。
- 利用先がバグを避けるために入れていた処理は、今回の修正で不要になったことを確かめてから外す。残すと二重に処理される。
- 外したことで出力の表記だけが変わり、意味が変わらない場合（書き出した文字列の書式は変わるが、読み込めば同じ値になるなど）、その表記に依存する箇所（テスト、文書、取り込み側のコード）が見つからなければ、元の表記を保つための引数や分岐は足さない。変化は報告に書く。

**テスト**: プロジェクトの方針に従い、今回変えた振る舞い・回帰・重要な境界条件を確かめる。期待値は要件から決め、テストを通すために既存の期待値やアサーションを弱めない。モックより実物や既存の fake を優先する。次のテストは足さない。

- 同じことを確かめるケース
- 再利用した既存の仕組み（HTTP の取得、リトライ、検証のヘルパーなど）の分岐（エラーの種類ごとの扱い、再試行の回数など）を、新しい呼び出し口から一つずつ確かめ直すテスト。新しいコードがその仕組みを正しく呼んでいることは確かめてよい
- 頼まれていない機能や防御処理のためだけのテスト。テストが要るほどの処理なら、その処理が本当に要るかを先に見直す

**リファクタリング**: 挙動を変えない。足りない分岐の確認を先に用意し、変更の前後で同じ結果になることを確かめる。依頼された範囲だけを整理し、クラス階層やルールの外部ファイル化のような構造は、読みやすさに必要なときだけ足す。

**依存の選定**: 新しい依存は、既存の手段で足りない理由と、保守・セキュリティ上の負担を説明できるときに選ぶ。

**設計相談**: 実装はしない。「先に固定する条件」を満たす最も小さい案と、それより大きな構造が必要になる条件を示す。

**差分レビュー**: ファイルを編集せずに指摘を返す。

- 正しさの問題は、過剰設計の指摘と分けて先に書く。
- 差分で増えた依存・抽象化・設定・防御コード・テストを、「足す前に問う」の表に照らして見る。
- 過剰設計の指摘は、何を消し、何に置き換えるかを具体的に書けるものに限る。形式は「`ファイル:行` — 何を消す／何に置き換える — 理由」。置き換えで挙動が変わりうる点は、見送らずに指摘に添える。
- プロジェクトの規約に沿っていることを、過剰設計として指摘しない。「もっと汎用的に」「拡張できるように」という方向の指摘はしない。

## 5. 依頼と手段が食い違うとき

| 状況 | 対応 |
| --- | --- |
| 依頼が目的だけを述べている | 最小十分な手段を選んで進める |
| ユーザーが手段や範囲を明示している | 明示どおりに作る。より簡単な代替は一文で提案するにとどめる |
| 明示された手段が正しさや安全性を損なう | 作る前に、問題・影響・代替案を示す |
| どちらを求めているか判断できず、後から戻しにくい | 着手前に質問する |

## 6. 完了前に変更を見直す

今回自分が加えた変更をすべて読み直す（Git なら `git diff` と新しいファイル）。

- 各変更が、要件・正しさ・規約・安全性のどれのためか言えるか。言えないものは消す
- 同じことをする既存コードがないか
- 使われなくなったコード、import、引数、試行錯誤の残骸が残っていないか
- 依頼と無関係な変更が混ざっていないか

見直しで削ったら、関係する検証をやり直す。

## 7. 報告とコメント

- 実装の報告は、変更点・確かめたこと・残る問題を短く書く。単純さを弁護する説明や、作らなかった機能の一覧は書かない。
- 省いたものは、ユーザーが期待していそうで、知らないと判断を誤るものだけ一文で書く。
- ユーザーが求めた説明（調査、設計の解説、手順）や、レビューの指摘に必要な根拠は省略しない。
- コードのコメントは、コードから読み取れない理由や制約だけを書き、変更の経緯は書かない。意図的に単純な方法を選んで既知の限界がある場合は、その限界と見直す条件をプロジェクトのコメント規約に沿って残す。
