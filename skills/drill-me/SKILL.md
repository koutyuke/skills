# Drill me

案を質問で掘り下げ、ユーザーと共通理解に至るためのスキル。対象は案であって人ではない。厳しく問うのは、あとで高くつく穴を今のうちに見つけるため。

このスキルの間は実装しない。成果物は、合意した内容のまとめ。

## 1. 題材をつかむ

- ユーザーの案を読み、目的・範囲・制約として何が書かれていて、何が書かれていないかを把握する
- 関係するコード、ドキュメント、設定、過去の決定（ADR など）、外部サービスの公式ドキュメントを自分で調べる。**事実を調べるのは自分の仕事で、ユーザーに聞くのは判断だけ**。調べればわかることを質問すると、ユーザーの時間を無駄にする
- 調べるのに時間がかかるなら、サブエージェントに任せてよい。調べている最中の事実は「まだ決まっていない前提」として扱い、それに左右される質問だけを待たせる。左右されない質問は先に出す

ただし、次の事実はユーザーに聞いてよい。判断を求める質問とは分けて、「確認したい事実」として聞く。

- ユーザーしか知らない事実（動機、使える時間や予算、組織の事情、利用状況の数字など）
- 手元に調べる手段がない事実（リポジトリがない、外部サービスの中身が見えないなど）

聞いても答えが得られない事実は、仮定で黙って埋めない。「未確認の前提」として置き、確かめる方法を添える。

## 2. 論点を依存関係で整理する

論点には順序がある。「どの DB を使うか」が決まらないと「スキーマをどう移行するか」は決められない。

- 決めるべき論点を洗い出し、「A が決まらないと B は決められない」という依存関係でつなぐ
- **今聞けるのは、前提になる論点がすべて決まっているものだけ**。前提が未決の論点を聞くと、ユーザーは仮定の上で答えることになり、あとで答えが無駄になる
- 依存しているとみなすのは、A の答えによって B の選択肢そのものが変わる場合や、B を聞く必要自体がなくなりうる場合。選択肢は変わらず推奨だけが変わるなら、「A が X なら Y」と条件つきの推奨を書いて同じラウンドで聞いてよい。A がユーザーに確認する事実でも同じ
- 「やるか・やらないか」がまだ決まっていないなら、やる場合の実施の細部（手順、移行方式など）は後のラウンドに回す
- ユーザーの答えで論点の構造は変わる。答えを受けるたびに整理し直す

## 3. ラウンドごとに質問する

今聞ける論点を 1 回のラウンドにまとめて出す。1 問ずつ往復すると時間がかかる。

- 1 ラウンドは 7 問までを目安にする。今聞ける論点がそれより多いなら、後から変えにくいもの、影響の大きいものを先に出し、残りは次のラウンドに回す
- 各質問には、推奨する答えとその理由を必ず添える。ユーザーは推奨を叩き台にでき、「推奨で OK」と返すだけで済む質問も多い
- ユーザーしか知らない事実を聞く質問では、推奨の代わりに、答え方の例（「週に何時間、いつまでに」など）と、答えがわからないときの扱いを示す
  - 値がどちらでも結論が変わらないなら、仮の値を置いて進めてよい
  - 値しだいで結論が変わるなら、仮の値で決めない。どの値を境に判断が変わるかと、確かめる方法を示し、確かめるまで未決にする

### 出し方

調べてわかった事実のうち、質問の前提になるものは、質問の前に短く共有する。ユーザーの案と食い違う事実（使えない基盤、守るべき規則など）は、特に先頭に置く。解釈がほぼ一つに決まり、違っても直しやすい点（「23 時」は日本時間、など）は質問にせず、「前提（違えば教えてほしい）」としてここに書く。

質問は次の形で文章にまとめる。ユーザーに確認したい事実がなければ、その見出しは省く。

```markdown
### ラウンド 2

**Q1. 失敗時の再実行をどこで持つか**
ジョブ単位で再実行すると、途中まで書き込んだデータが二重になる可能性がある。
選択肢: (a) ジョブ単位で冪等にする (b) レコード単位で再開位置を記録する
→ 推奨: F1 が 1 日 1 万件以下なら (a)。再開位置の管理を持たずに済む

**Q2. ...**

#### 確認したい事実

**F1. 1 日に処理する件数はどのくらいか**
答え方の例: 「平均 5 千件、月末は 3 万件」
→ わからなければ: 1 万件を超えるかどうかで Q1 の答えが変わるので、確かめるまで Q1 は未決にする。既存システムのログで直近 1 か月の件数を見る
```

`AskUserQuestion` のような選択式の質問ツールが使えて、ラウンドの質問がすべて背景説明なしで選べる選択式なら、そのツールで出してもよい。その場合は推奨を先頭の選択肢に置き、推奨であることをラベルで示す。1 回で出せる問数に上限があるなら、重要なものから出す。

### よい質問の条件

- 1 問で 1 つの論点だけを聞く
- 答えによって、その後の設計や作業が変わる。どう答えられても何も変わらない質問は出さない
- 抽象的な「どう思いますか」ではなく、選べる形か、具体的な状況で聞く

## 4. 弱点を突く視点

毎ラウンド、次の視点から案に当てはまるものを選んで質問にする。全部を機械的に聞く必要はない。

| 視点           | 問いの例                                                             |
| -------------- | -------------------------------------------------------------------- |
| 前提の反証     | その前提が崩れたら何が起きるか。前提は確かめたのか、思い込みか       |
| 失敗の先取り   | 半年後にこの案が失敗していたとしたら、最もありそうな原因は何か       |
| 代替案         | ほかの方法と比べたか。「やらない」「今はやらない」案と比べてどうか   |
| 規模と運用     | データ量や利用者が10倍になったら。障害時に誰がどう気づき、どう戻すか |
| 可逆性         | 間違っていたとき、後から戻せるか。戻せない部分はどこか               |
| 安全とデータ   | 権限、秘密情報、個人情報、データの整合性に影響はあるか               |
| 影響を受ける人 | 誰の作業や体験が変わるか。その人は知っているか                       |
| 成功の判定     | 何をもって成功とするか。それはどう測るか                             |

## 5. 答えの扱い方

| 答え                                                           | 扱い                                                                                             |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 「たぶん」「とりあえず」「あとで考える」                       | 決定ではなく未決として扱う。未決のまま進めてよいかを確かめる                                     |
| 「おまかせ」「推奨で」                                         | 推奨を採用し、ユーザーに任されて決めたことを明記して決定に入れる                                 |
| ほかの決定や、同じラウンドのほかの答えと矛盾する               | すぐに指摘し、どちらを採るかを聞く                                                               |
| 規程・法令・契約・セキュリティ方針など、守るべき決まりに反する | 決定として受け入れない。根拠（どの文書のどこか）を示して未決にし、決まりの範囲に収まる代案を出す |
| 過去の設計判断（ADR など）と食い違う                           | ユーザーが覆すと決めたなら受け入れる。ただし、元の記録の更新や関係者への確認を次の一手に入れる   |
| 推奨と違うが、上のどれにも当たらない                           | リスクを一文で伝えたうえで受け入れ、先に進む。同じ論点を蒸し返さない                             |
| 弱い、根拠が薄い                                               | 同じ論点をもう一段掘り下げる。ただし同じ質問の繰り返しではなく、角度を変える                     |

- **決定はユーザーのもの**。推奨を変えるのは、新しい事実や根拠が出たときだけ。ユーザーが反対しただけでは変えない
- 口調は率直に、でもからかわない。弱点を指摘するのは案をよくするためであって、言い負かすためではない

## 6. 終わり方

次のどちらかで終える。

- 今聞ける論点がなくなった（すべての論点が決定済みか、ユーザーが未決のままでよいと判断した）
- ユーザーが「ここまででいい」と言った

ユーザーが打ち切ったときに、矛盾や決まりへの違反が残っていても、新しいラウンドは始めない。まとめの冒頭でそれを指摘し、代案があれば選択肢として添えて未決事項に載せる。

終えるときは、次の形でまとめる。

```markdown
## まとめ

### 目的

### 決定事項

- <決定>（理由: <なぜそう決めたか>）

### 前提

- 確認済み: <調べて確かめた前提>
- 未確認: <確かめていない前提と、確かめる方法>

### 未決事項

- <論点>（決めないまま進めたときの影響）

### リスクと対策

### 次の一手
```

途中で打ち切った場合は、まだ聞いていない論点も未決事項にすべて載せる。黙って仮定を置いたまま終えない。

ユーザーがまとめの内容に合意するまでは、実装や作業に入らない。

## 7. 記録に残す（任意）

まとめを見せたあと、残す価値がありそうなら文書化を提案する。ADR（設計判断の記録）、用語集、設計文書などが候補。

- 置き場所と形式は、リポジトリにある既存の慣習（`docs/adr/` など）に合わせる。なければ、ユーザーに場所を確認する
- ユーザーが同意したときだけ書く
