# Drill me

次の行動（実装、提案、依頼など）に入る前に、ユーザーと同じものを思い描いている状態を作るためのスキル。そろえるのは、目的、今回決める範囲、重要な決定とその理由、具体的な場面での結果、まだ決まっていないこととその扱い。

厳しく問う対象は案であって人ではない。価値は質問の数や反論の強さではなく、あとで高くつくずれを今見つけられたかで決まる。このスキルの間は実装しない。成果物は合意した内容のまとめ。

## 1. 調べてから聞く

- 依頼と会話から、目的・今回決めること・制約・対象外を読み取る。すでに書かれていることは聞き直さない。
- 関係するコード、文書、設定、過去の決定（ADR など）を自分で調べる。調べてわかる事実はユーザーに聞かない。
- 調べた事実のうち、案と食い違うもの（使えない基盤、守るべき規程、既存の決定、案の前提と違う現状）は、最初のメッセージの冒頭に書く。案の前提が変わるので、細部の質問より先に共有する。

## 2. 聞くことを選ぶ

不明点ごとに、扱いを決める。

| 不明点 | 扱い |
| --- | --- |
| 調べればわかる事実 | 自分で調べ、結果だけ共有する |
| ユーザーしか知らない事実・事情（動機、予算、期限、組織の事情、利用状況の数字） | 聞く。推奨値は置かず、答え方（単位や粒度）と、わからないときの扱いを添える |
| ユーザーが決めること（方針、優先順位、トレードオフの選択） | 聞く。選択肢と、根拠がそろっていれば推奨を添える（§4） |
| 会話では決まらないこと（使い心地、実際の性能、他の人の意向） | 聞き続けない。試作・計測・関係者への確認を「確かめ方」として未決事項に残す |
| どう決まっても次の行動が変わらない、または後で簡単に直せる細部 | 聞かない。結果に関わるなら仮定としてまとめに書く |

質問にするのは、答えによって目的・範囲・設計・作業・リスクのどれかが変わる論点だけ。重要な不明点がなければ、質問せずにまとめへ進んでよい。

優先するのは、外れたときの損失が大きいもの、根拠が弱いもの、後から戻しにくいもの、ほかの論点の前提になるもの。

## 3. 依存関係の順に聞く

- A の答えで B の選択肢や、B を聞く必要そのものが変わるなら、B は A が決まってから聞く。「やるかどうか」が決まっていなければ、やる場合の細部は聞かない。
- A の答えで推奨だけが変わり、選択肢は変わらないなら、「A が X なら Y」と条件付きの推奨にして同じメッセージで聞いてよい。
- 何を満たせばよいか（許容できる遅延、重複を許すか、期限など）は、どの手段を選ぶかに依存しないことが多い。手段が決まっていなくても聞ける。
- 答えを受けるたびに論点を整理し直し、不要になった質問は捨てる。

## 4. 聞き方

- 1 回のメッセージで出す質問は 3 問まで。今聞ける論点がそれより多いときは優先度の高いものから出し、残りの論点の数と主なものを一行で示す。説明や比較が要る重い判断と同じメッセージに入れるのは、それと独立していて短く答えられる質問だけにする。
- 1 問で 1 つの論点を聞く。番号は会話全体の通し番号にする。
- 選択肢は、選んだ結果がわかる言葉で書く。「A でよいですか」のように、推奨への同意を「はい」で答えさせる形にしない。選択肢にない答え、保留、「おまかせ」も受け付ける。
- 推奨を添えるのは、ユーザーの判断基準がわかっていて、選択肢を比べる材料がそろっているとき。推奨、理由、推奨が変わる条件を短く書く。何を優先したいか、何に困っているかがまだわからない段階では、推奨を付けずにそれを先に聞く。
- 抽象的な言葉（「速く」「安全に」「完了」「両方」）のまま合意しそうなときは、具体的な場面と結果に言い換えて確かめる。例: 「同じファイルを 2 回取り込んでも件数は増えない、という理解で合っていますか」

メッセージは次の形にする。調べた事実の共有、確認したい事実、残りの論点は、該当するものがなければ省く。

```markdown
調べてわかったこと: 通知は 1 日 2 回のバッチで送っている（`jobs/notify.ts`）。docs/adr/0007 で、外部への送信はすべて監査ログに残すと決まっている。

**Q3. 送信に失敗した通知をどう再送するか**
バッチ単位で再送すると、途中まで送った分が二重に届く。
- (a) バッチ単位で再送し、送信済みの宛先は記録して飛ばす
- (b) 1 件ずつキューに入れ、失敗した分だけ再送する
→ 推奨: (b)。送信済みの記録を別に持たずに済む。1 日の件数が数百件程度なら (a) でも足りる

**Q4. 1 日に送る件数（確認したい事実）**
答え方の例: 「平均 5,000 件、月末は 3 万件」。わからなければ、そう書いてください
→ Q3 の推奨は、1 万件を超えるかどうかで変わります

残りの論点: 2 つ（失敗の検知方法、移行の手順）。Q3 が決まってから聞きます。
```

選択式の質問ツール（`AskUserQuestion`、`request_user_input` など）が使えて、質問が短い選択で答えられるなら、ツールで聞いてよい。問数や選択肢数はツールの制限に従い、前提の説明が要るなら先に本文で共有する。ツールが返さなかった回答、既定値、タイムアウトは同意として扱わない。

## 5. 答えを受け取ったら

次のメッセージの冒頭で、今回決まったことを短く書き戻してから先へ進む。数値・条件・例外は、ユーザーの言葉のまま残す。

| 答え | 扱い |
| --- | --- |
| 選択・はっきりした回答 | 決定として記録する（理由も） |
| 「おまかせ」「推奨で」 | 推奨を採用し、任されて決めたと記録する。任されたのはその論点だけ |
| 「とりあえず A」「たぶん A」 | 文脈で読む。A で進める意思がはっきりしていれば暫定の決定とし、見直す条件を確かめる。迷っているだけなら未決 |
| 「あとで考える」 | 未決。決めないまま進めたときの影響を伝え、まとめに残す |
| 無回答・一部だけの回答 | 答えた論点だけ更新する。無回答は同意ではない |
| ほかの決定や、同じメッセージのほかの答えと矛盾する | すぐ指摘し、どちらを採るかを聞く。解けるまで、矛盾に関わる論点は決定にしない |
| 規程・法令・契約・セキュリティ方針に反する | 決定として受け入れない。どの文書のどこに反するかを示し、範囲内の代案を出す。文書の適用範囲が不確かなら、それも確かめる |
| 過去の決定（ADR など）と食い違う | ユーザーが覆すと決めたなら受け入れ、記録の更新や関係者への確認を次の一手に入れる |
| 推奨と違うが、上のどれにも当たらない | リスクを一文で伝えて受け入れる。同じ論点を蒸し返さない |
| 根拠が薄い | 判断が変わりうる重要な論点だけ、角度を変えてもう一度聞く。それでも決まらなければ、確かめ方を添えて未決にする |

推奨を変えるのは、新しい事実が出たとき、自分の推論の誤りに気づいたとき、ユーザーの優先順位や価値観が新しくわかったとき。反対されたことだけを理由に変えない。決定はユーザーのもので、言い負かすことが目的ではない。

## 6. 弱点を探す観点

質問の候補を探すときに使う。全部を聞く必要はなく、聞くかどうかは §2 で選ぶ。

- 前提: その前提が崩れたら何が起きるか。確かめたのか、思い込みか
- 失敗の先取り: 半年後にこの案が失敗していたら、最もありそうな原因は何か
- 代替案: ほかの方法、「やらない」「今はやらない」「小さく試す」と比べたか
- 戻しやすさ: 間違っていたら戻せるか。戻せない部分はどこか
- 運用: 障害時に誰がどう気づき、どう戻すか。量が増えたらどうなるか（今回の判断に関わる場合だけ）
- 安全とデータ: 権限、秘密情報、個人情報、データの整合性に影響はあるか
- 影響を受ける人: 誰の作業や体験が変わるか。その人は知っているか
- 成功の判定: 何をもって成功とし、どう測るか

## 7. 終わり方

次のどちらかになったら、まとめを出す。

- 残っている論点が、どう決まっても次の行動を変えない。または、いつ・どう確かめるかが決まった
- ユーザーが「ここまででいい」と言った。新しい質問はしない

調査待ち・確認待ちの論点が残っているときは、完了とは書かず、確認待ちがあることをまとめに明記する。

```markdown
## まとめ

（未解決の矛盾や、規程との衝突が残っていれば、ここに選択肢つきで先に書く）

**目的**: <一文>

**決定事項**
- <決定>（理由。おまかせで決めたものは「おまかせ」と書く）

**前提**
- 確認済み: <調べて確かめたこと>
- 未確認: <確かめていないこと>（確かめ方）

**未決事項**
- <論点>（決めずに進めたときの影響。確かめ方や決める時期）

**リスク**
- <リスク>（対策）

**次の一手**
- <誰が何をするか>
```

- 空の項目は省く。各項目は 1〜2 文で書き、経緯や推論の説明は判断に必要な分だけにする。
- 互いに矛盾する答えは、片方も決定事項に入れず、冒頭の未解決に両方を書く。
- 途中で打ち切った場合は、まだ聞いていない論点も未決事項に載せる。
- 会話に出ていない決定や仮定を、まとめで新しく足さない。
- ユーザーがまとめを確認するまで、実装や作業に入らない。最初の依頼に「まとまったら実装まで」が含まれていれば、確認のあとはその依頼に従い、改めて承認を求めない。

まとめのあと、戻しにくく、理由が自明でなく、代替案と比べて決めた決定があれば、ADR などへの記録を提案してよい。置き場所と形式はリポジトリの慣習に従い、ユーザーが同意したときだけ書く。
