# Drill me

共通理解に達するまで、ユーザーを徹底的に問い詰める。

決めることの全体を**論点ツリー**として捉え、各論点は、その答えを前提にする下位の論点へ枝分かれしていく。

質問は**ターン**単位で進める。前提となる論点がすべて決まっていて、まだ聞いていない答えを推測せずに聞ける論点を**今聞ける論点**と呼ぶ。1 ターンで今聞ける論点をすべて聞き、回答を待ってから次のターンに進む。

回答が出るたびに論点ツリーは変わる。決まった論点は、それを前提にしていた論点を今聞ける状態にする。今聞ける論点を洗い直し、次のターンで聞く。同じターンでまだ答えの出ていない質問に依存する論点は、このターンではなく後のターンで聞く。

事実を集めるのはエージェントの仕事で、ユーザーの仕事ではない。今聞ける論点に環境の事実（ファイル、ツールなど）が必要なら、新しいコンテキストのサブエージェントに調べさせる。調べればわかることはユーザーに聞かない。調査の完了は待たない。実行中の調査は未決の前提として扱い、それに依存する論点だけを後回しにして、残りの今聞ける論点は今聞く。一方、決めることはユーザーのものだ。一つずつ質問として出し、回答を待つ。

## 質問の出し方

ユーザーへの質問は、ハーネスに組み込まれた質問機能（Claude Code の `AskUserQuestion`、Codex の `request_user_input` など）で出す。本文に質問を書いて返信を待つ形にしない。質問機能がないハーネスでだけ、同じ項目を本文に書く。

1 回の呼び出しで出せる問数、選択肢の数、ラベルの長さはツールの定義に従う。今聞ける論点が上限を超えるときは、同じターンの中で続けて呼び出す。

### 回答形式

質問ごとに回答形式を選ぶ。

| 形式     | 使う場面                                                                       | ツールでの出し方                                                                                                                                                            |
| -------- | ------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 単一選択 | 選択肢が互いに排他的な決定                                                     | 単一選択で出す（`AskUserQuestion` なら `multiSelect: false`）                                                                                                               |
| 複数選択 | 対象に含める機能や範囲など、同時に複数を選べる決定                             | 複数選択で出す（`multiSelect: true`）。ツールが対応していなければ、組み合わせが少ないときは組み合わせを選択肢にし、多いときは「その他」に複数書いてもらうよう質問文で伝える |
| 自由記述 | 数値、期限、名前、動機など、ユーザーしか知らない事実で選択肢を列挙できないもの | 自由入力欄があれば使う。なければ目安になる範囲や代表値と「わからない」を選択肢にし、正確な値は「その他」に書いてもらう                                                      |

選択式の質問でも、ユーザーが「その他」として自由に書けるようにする。ツールが自動で追加する場合（`AskUserQuestion` など）は自分で足さない。追加しないツールでは、最後の選択肢を「その他（自由記述）」にする。

コード、ASCII 図、UI レイアウト、設定ファイル、ディレクトリ構成など、見比べると違いがわかる選択肢には、ツールのプレビュー機能（`AskUserQuestion` の `preview` など）を積極的に使う。プレビューを使えない場合は、選択肢の説明に違いの要点を書く。

### 推奨案

その選択肢を取れば、今の作業を終えた時点で最良の結果になると見通せるときだけ、ラベルの末尾に `(Recommended)` を付ける。例: `たい焼きを食べる (Recommended)`。基準は目先の手軽さではなく、作業を終えたときの結果である。

推奨は必須ではない。ユーザーの優先順位がわからない、または比べる材料が足りないときは付けず、その判断基準を先に聞く。

推奨案は選択肢の先頭に置き、説明に理由を一文で書くこと。単一選択では推奨は 1 つまで。複数選択では推奨する項目それぞれに付ける。
推奨案に「はい」と答えさせる問い方（「A でよいですか」）にしない。選択肢を並べて選んでもらう。

### 質問 ID

質問には会話全体で通しの ID を振り、あとから見返しても質問同士の関係がわかるようにする。

新しい論点には、それまでの最大の整数の次を振る(`Q1`、`Q2`、`Q3` …)。前のターンの質問 `X` の回答がなければ生まれなかった質問（回答の意味の確認、具体化、深掘り、その回答で生じた下位の論点）には `X.Y` を振る。`Q3` から派生すれば `Q3.1`、`Q3.2`、`Q3.1` からさらに派生すれば `Q3.1.1` とする。
回答が得られなかった質問を聞き直すときは、同じ ID を使う。それ以外で ID を使い回さない。

### 各項目の書き方

ユーザーには質問のダイアログしか見えていないことがある。各質問は、それだけで判断できるように書く。

| 項目           | 書き方                                                                                                             |
| -------------- | ------------------------------------------------------------------------------------------------------------------ |
| ヘッダー       | `Q<ID> <論点を表す短い名詞>`。例: `Q3 再送方式`                                                                    |
| 質問文         | 1 行目に決めることを一文の疑問形で書く。2 行目以降に、判断に必要な背景と、答えによって何が変わるかを 1〜2 文で書く |
| 選択肢のラベル | 選んだ結果がわかる短い言葉。「A 案」「はい」のような中身のない言葉にしない。推奨案にはタグを付ける                 |
| 選択肢の説明   | 選んだら何が起きるか、何を引き換えにするか。推奨案には推奨する理由も書く                                           |
| プレビュー     | 見比べると違いがわかるときに、コード・図・レイアウトを入れる                                                       |

フォーマット:

```text
[Q<ID>] <論点を表す短い名詞>

<質問文>

<選択肢>
```

単一選択の例:

```text
[Q3] 再送方式

送信に失敗した通知をどう再送しますか？
いまはバッチ単位で送っているため、そのまま再送すると途中まで送った分が二重に届きます。

選択肢:
  1. 失敗分だけ再送 (Recommended)
     1 件ずつキューに入れ、失敗した分だけ再送する。送信済みの記録を別に持たずに済む。
  2. バッチごと再送
     送信済みの宛先を記録して飛ばす。キューは要らないが、記録用のテーブルが増える。
```

自由記述の例:

```text
[Q4] リリース期限

本番リリースの期限はいつですか？
期限によって、移行を一度に行うか段階的に行うかが変わります。正確な日付は「その他」に書いてください。

選択肢:
  1. 今月中
  2. 来月中
  3. 期限なし
  4. わからない
```

### ターンの本文

質問機能を呼び出す前に、本文に次の内容を短く書く。会話をあとから見返したときの記録になる。該当しない項目は省く。

```markdown
**決まったこと**: Q3 再送方式 = 失敗分だけ再送（推奨を採用） / Q4 リリース期限 = 来月中
**調べてわかったこと**: 通知は 1 日 2 回のバッチで送っている（`jobs/notify.ts`）
**後で聞く論点**: Q5 の回答待ち 1 件、調査中 1 件（送信ログの保存先）
```

## 回答の扱い

- 「その他」に書かれた内容は、ユーザーの言葉のまま決定として記録する。
- 無回答、ツールのタイムアウト、既定値の自動選択は同意として扱わない。その論点は未決のまま残し、次のターンで同じ ID で聞き直す。
- 回答がほかの決定と矛盾するときは、矛盾を `X.Y` の質問として示し、どちらを採るか選んでもらう。

## 終わり方

今聞ける論点がなくなり、論点ツリーのすべての枝をたどり終え、黙って仮定したことが残っていなければ問い詰めを終える。決まったことを ID 付きで一覧にし（例: `Q3 再送方式: 失敗分だけ再送`）、質問機能で共通理解に達したかを確認する。ユーザーが確認するまで、決まった内容に基づく作業に入らない。
