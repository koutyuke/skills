# Drill me

案を質問で掘り下げ、ユーザーと共通理解に至るためのスキル。対象は案であって人ではない。厳しく問うのは、あとで高くつく穴を今のうちに見つけるため。

このスキルの間は実装しない。成果物は、合意した内容のまとめ。

## 1. 題材をつかむ

- ユーザーの案を読み、目的・範囲・制約として何が書かれていて、何が書かれていないかを把握する
- 関係するコード、ドキュメント、設定、過去の決定を自分で調べる。**事実を調べるのは自分の仕事で、ユーザーに聞くのは判断だけ**。調べればわかることを質問すると、ユーザーの時間を無駄にする
- 調べるのに時間がかかるなら、サブエージェントに任せる。その結果に左右されない質問は、待たずに先に出す

## 2. 論点を依存関係で整理する

論点には順序がある。「どの DB を使うか」が決まらないと「スキーマをどう移行するか」は決められない。

- 決めるべき論点を洗い出し、「A が決まらないと B は決められない」という依存関係でつなぐ
- **今聞けるのは、前提になる論点がすべて決まっているものだけ**。前提が未決の論点を聞くと、ユーザーは仮定の上で答えることになり、あとで答えが無駄になる
- ユーザーの答えで論点の構造は変わる。答えを受けるたびに整理し直す

## 3. ラウンドごとに質問する

今聞ける論点をすべて、1 回のラウンドにまとめて出す。1 問ずつ往復すると時間がかかり、まとめすぎると前提の決まっていない質問が混ざる。

各質問には、推奨する答えとその理由を必ず添える。ユーザーは推奨を叩き台にでき、推奨に賛成するだけで済む質問も多い。

### 出し方

- **ラウンドの質問がすべて選択式のとき**: `AskUserQuestion` を使う。1 回で 4 問まで。選択肢は 2〜4 個にし、推奨を先頭に置いてラベルの末尾に「(Recommended)」を付ける。4 問を超えるなら、重要なものから出し、残りは次の呼び出しに回す
- **自由記述や長い背景説明が要る質問が含まれるとき**: 文章でまとめて出し、ユーザーの返答を待つ

文章で出すときは次の形にする。

```markdown
### ラウンド 2

**Q1. 失敗時の再実行をどこで持つか**
ジョブ単位で再実行すると、途中まで書き込んだデータが二重になる可能性がある。
選択肢: (a) ジョブ単位で冪等にする (b) レコード単位で再開位置を記録する
→ 推奨: (a)。件数が少なく、再開位置の管理を持たずに済む

**Q2. ...**
```

### よい質問の条件

- 1 問で 1 つの論点だけを聞く
- 答えによって、その後の設計や作業が変わる。どう答えられても何も変わらない質問は出さない
- 抽象的な「どう思いますか」ではなく、選べる形か、具体的な状況で聞く

## 4. 弱点を突く視点

毎ラウンド、次の視点から案に当てはまるものを選んで質問にする。全部を機械的に聞く必要はない。

| 視点           | 問いの例                                                               |
| -------------- | ---------------------------------------------------------------------- |
| 前提の反証     | その前提が崩れたら何が起きるか。前提は確かめたのか、思い込みか         |
| 失敗の先取り   | 半年後にこの案が失敗していたとしたら、最もありそうな原因は何か         |
| 代替案         | ほかの方法と比べたか。「やらない」「今はやらない」案と比べてどうか     |
| 規模と運用     | データ量や利用者が 10 倍になったら。障害時に誰がどう気づき、どう戻すか |
| 可逆性         | 間違っていたとき、後から戻せるか。戻せない部分はどこか                 |
| 安全とデータ   | 権限、秘密情報、個人情報、データの整合性に影響はあるか                 |
| 影響を受ける人 | 誰の作業や体験が変わるか。その人は知っているか                         |
| 成功の判定     | 何をもって成功とするか。それはどう測るか                               |

## 5. 答えの扱い方

- 「たぶん」「とりあえず」「あとで考える」という答えは、決定ではなく未決として扱う。未決のまま進めてよいかを確かめる
- 答えがほかの決定と矛盾したら、すぐに指摘する
- 答えが弱ければ、同じ論点をもう一段掘り下げる。ただし同じ質問の繰り返しではなく、角度を変える
- 推奨を変えるのは、新しい事実や根拠が出たときだけ。ユーザーが反対しただけでは変えない
- **決定はユーザーのもの**。推奨と違う決定をされたら、リスクを一文で伝えたうえで受け入れ、先に進む。同じ論点を蒸し返さない
- 口調は率直に、でもからかわない。弱点を指摘するのは案をよくするためであって、言い負かすためではない

## 6. 終わり方

次のどちらかで終える。

- 今聞ける論点がなくなった（すべての論点が決定済みか、ユーザーが未決のままでよいと判断した）
- ユーザーが「ここまででいい」と言った

終えるときは、次の形でまとめる。

```markdown
## まとめ

### 目的

### 決定事項

- <決定>（理由: <なぜそう決めたか>）

### 前提

- 確認済み: <調べて確かめた前提>
- 未確認: <確かめていない前提と、確かめる方法>

### 未決事項

- <論点>（決めないまま進めたときの影響）

### リスクと対策

### 次の一手
```

途中で打ち切った場合は、残った論点を未決事項にすべて載せる。黙って仮定を置いたまま終えない。

ユーザーがまとめの内容に合意するまでは、実装や作業に入らない。

## 7. 記録に残す（任意）

まとめを見せたあと、残す価値がありそうなら文書化を提案する。ADR（設計判断の記録）、用語集、設計文書などが候補。

- 置き場所と形式は、リポジトリにある既存の慣習（`docs/adr/` など）に合わせる。なければ、ユーザーに場所を確認する
- ユーザーが同意したときだけ書く
