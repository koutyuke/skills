# Docs That Work

初めて読む人が、少ない読解で全員同じ全体像を持ち、迷わず判断・行動できる文書にする。

- 人は長い文章を読まない。長いほど最初に読むのをやめ、考えるのもやめる。詳しく書いたのだから読まない人が悪い、という文書は失敗である。
- 読んだ人によって思い浮かべる像や行う作業が変わる文書も失敗である。そのずれは問い合わせの増加や、誤った作業による事故になる。

## 完成形

1. タイトル: 何の文書か分かる名前（「〜する手順」「〜の調査報告」）
2. 要約: 1〜3 行。何の文書か、結論、読者がすること
3. 全体図: 3 つ以上の要素の関係、作業の順序、分岐のどれかがあるときに置く
4. 本文: 読者が作業・判断する順に書く。分岐した先は分岐元の配下に置く

例（一部省略）:

````markdown
# ステージング DB を前日のバックアップに戻す手順

ステージング DB を前日 03:00（JST）のバックアップに戻す手順である。所要時間は約 20 分で、その間ステージングは使えない。作業者には `stg-admin` 権限が必要である。

```text
[1. 停止を告知する]
        │
        ▼
[2. 復元する]
        │
        ▼
[3. 件数を確かめる] ──一致しない──▶ [3-1. 切り戻す]
        │ 一致する
        ▼
[4. 再開を告知する]
```

## 1. 停止を告知する

Slack の `#stg-ops` に「10:00〜10:20 ステージング停止（DB 復元）」と投稿する。

## 3. 件数を確かめる

`psql "$STG_DB_URL" -c 'select count(*) from orders;'` の結果を、`#stg-ops` に毎朝 09:00 に投稿される前日件数と比べる。

- 一致する: 4 へ進む。
- 一致しない: 4 へ進まず、次の手順で切り戻す。
  1. `./scripts/restore.sh --snapshot pre-restore` を実行する。
  2. `#stg-ops` に `@sre-oncall` 宛てで、手順 3 の 2 つの件数を投稿する。
````

## 書く手順

### 1. 読者と用途を決める

- 誰が、どの場面で読み、読んだ後に何を判断・実行するかを決める。読者が知らない前提（社内用語、会話の中で決めた呼び名、作業中に分かったこと）を洗い出す。
- 文書の種類を決め、[references/doc-types.md](references/doc-types.md) の該当する節を読む。構成・言語・表記は、同じ場所のテンプレートや同種の文書、プロジェクトの規約、依頼者の指示や設定に合わせる。
- 既存の文書を直すときは、依頼された箇所と、その変更で食い違う箇所だけを直す。正しい部分は書き換えない。

### 2. 材料をふるいにかける

その文を消したら、初めて読む人の今後の判断・行動が変わるかで判定する。変わらない文は書かない。

| 本文に書く                                 | 本文に書かない                                     |
| ------------------------------------------ | -------------------------------------------------- |
| 現在の結論、仕組み、条件、手順             | 調べた順序、途中の仮説、試して戻したこと           |
| 判断の理由、制約、リスク                   | 「A ではなく、B でもない」という除外の列挙         |
| 読者の判断を左右する未確認事項             | 再現しなかった事実、訂正の経緯、会話への返答       |
| ADR・設計文書の却下案（案と理由を各 1 行） | diff・コード・リンク先を読めば分かることの言い換え |

- 書かない例: 「最初はキャッシュを疑ったが違った。DNS でもなかった。調べた結果、コネクションプールの枯渇が原因と分かった。」
- 書く例: 「原因はコネクションプールの枯渇です。ピーク時に 35 接続が必要でしたが、上限は 20 でした。」

結論に至るまでに捨てたもの（除外した原因、再現しなかった試行、採用しなかった方法とその理由）は、根拠、前提条件、注意、未確認事項などに形を変えても書かない。例外は ADR・設計文書の却下案だけである。結論の確度は「確認済み」「推測」「未確認」と、確かめる方法で示す。

確かでない情報と、資料にない情報は次のように扱う。

- 未確認事項は、何が分かっていないかと、確かめる方法だけを書く。確かめようとした経緯は書かない。確かめる方法が資料にない場合は、提案として書く。
  - 書かない例: 「ローカルで 3 回負荷をかけたが再現しなかった。テスト環境でも再現しなかった。」
  - 書く例: 「再現は未確認です。本番と同じ 1 万件のデータで負荷をかけて確かめます。」
- 資料にない情報は、読者の判断・行動を左右する場合だけ「未定」「未確認」と書く。左右しない場合（判断に関係しない時刻のタイムゾーンなど）は触れない。
- 資料にない一般知識（前提となる設定など）を足す場合は、確定した事実として書かず、未確認の項目として書く。
- 資料の誤りや資料どうしの食い違いに気づいたら、本文には確かな内容だけを書く。食い違いは完了報告で依頼者に伝える。

本文から外した情報のうち、依頼者の判断に影響するもの（実施した検証、未解決の疑問、資料の誤りや食い違い）は、文書ではなく作業の完了報告に書く。

### 3. 骨組みを作る

- 見出しを、読者が作業・判断する順に並べる。調べた順や書きやすい順に並べない。
- 見出しは中身を言い切る。「概要」「その他」ではなく、「原因はコネクションプールの枯渇」「DB を復元する」と書く。見出しだけを順に読んで筋が通るようにし、階層は 3 段までにする。
- 「X の場合は A、Y の場合は B」という分岐は、分岐を判断する箇所の配下に A と B を書く。文書の別の場所に散らさない。分岐先が長い場合は別の文書に分けてよいが、分岐元に移る条件と移動先を書く。

### 4. 全体図を描く

- 3 つ以上の要素の関係、作業の順序、分岐のどれかがある文書は、要約の直後に全体図を置く。図にする関係がない文書（小さな PR、1 件の連絡）には置かない。
- 全体図には、文書の章立てではなく対象そのもの（構成要素のつながり、作業の流れ、原因の連鎖）を描く。要素名は本文で使う名前と一致させる。読む方向は上から下か左から右の一方にそろえ、視線が行き来しない配置にする。
- 全体図は 15 行程度までにする。手順が多い場合は、手順を段階にまとめ、段階と分岐と止める地点だけを描く。手順ごとの細部は本文に任せる。8 手順の例:

  ```text
  [準備: 1〜3] ──検証環境で失敗──▶ [中止]
        │
        ▼
  [本番反映: 4〜6]
        │
        ▼
  [確認: 7] ──NG──▶ [切り戻し: 7-1]
        │ OK
        ▼
  [後片付け: 8]
  ```

- 罫線と矢印の ASCII 図を、言語指定 `text` のコードブロックで描く。縦にそろえる記号（`│` `▼` など）は、その左側が半角文字だけになる列に置く。日本語は環境によって表示幅が変わり、右側にある記号の位置がずれるためである。幹を左端に置き、枝を右へ伸ばすと崩れない。
- 要素がおよそ 10 個を超える図、線が交差する図、3 者以上のやり取りの順序、状態遷移は Mermaid で描く。Slack やコミットメッセージなど Mermaid を表示できない場所では、ASCII 図に収まるよう図を分ける。
- 図の種類と描き方の詳細は [references/diagrams.md](references/diagrams.md) にある。

### 5. 本文を書く

- 未定義語を残さない。未定義語とは、人によってやり方が変わる言葉（「作成する」「連絡する」「確認する」「対応する」「設定する」「適宜」「など」「必要に応じて」）である。誰が、どこで、何を使って、何をし、何をもって完了とするかを書く。
  - 「担当者に連絡する」は「`#payments-oncall` に障害の URL と影響件数を投稿する」と書く。
  - 「動作を確認する」は「`curl -s localhost:8080/health` の結果が `ok` であることを確かめる」と書く。
  - 資料から分からないことは推測で埋めず、「未定: 連絡先（決める人: 決済チーム）」のように未定と書く。
- 一文に一つの内容を書き、誰が何をするかを明示する。数量・期限・条件は、数値や固有名で書く。
- 言い切る。確かでないことは「未確認」「推測（根拠: …）」と書き、「〜かもしれません」でぼかさない。
- 同じものは同じ語で呼び、言い換えない。
- 箇条書きは並列の項目と手順に使い、理由や因果は文章でつなぐ。太字・注意書き・絵文字は、見落とすと事故になる箇所だけに使う。
- 取り消せない操作やデータが失われる操作には、その操作の直前に、失われるものと避ける方法を書く。操作の後に書かない。
- 「現在」「最新」「新しい」ではなく、日付やバージョンを書く。
- 書き終えたら [references/sentences.md](references/sentences.md) で文を見直す。

量の目安を超えたら、分割、正本へのリンク、削除を検討する。必要な前提、理由、切り戻しは削らない。

| 対象                             | 目安                                    |
| -------------------------------- | --------------------------------------- |
| 要約                             | 1〜3 行                                 |
| 全体図                           | 15 行程度まで                           |
| 1 文                             | 60 字程度まで                           |
| 1 段落                           | 1 つの論点、3〜5 文                     |
| 箇条書き                         | 3〜7 項目。2 項目以下なら文にする       |
| PR・Issue の本文、Slack への投稿 | 1 画面（30 行程度）まで                 |
| 手順の 1 ステップ                | 1 つの操作、1〜2 文                     |
| 1 文書                           | 1 つの目的。目的が 2 つになったら分ける |

### 6. 正しさを確かめる

- コマンド、パス、URL、バージョン、設定値は、実行するか、正本（コード、設定、公式文書）を参照して確かめる。外部への書き込みや破壊的な操作は、承認なしに実行して確かめない。
  - 確かめられないものは本文に「未検証」と書く。同じ理由で未検証のものが多い場合は、要約か前提条件に 1 回まとめて書く。
  - 作業の記録（依頼者や自分が実行したコマンドと結果）に残っている結果は、確認済みとして書いてよい。
- 担当者、期限、影響の数値、理由を推測で埋めない。
- 元の情報の強さと範囲を保つ。「一部の環境で」を「常に」に、「推奨」を「必須」に変えない。
- データを変更・削除する手順で、安全に判断するための情報（判定基準、連絡先、切り戻し方法など）が欠けている場合も、資料から分かる手順は最後まで書き、欠けている箇所には「未定」と書く。
  - 止める地点は、欠けた情報がないと安全に行えない操作（データの変更、利用者への影響、取り消せない操作）のうち、最初のものの直前にする。それより前の手順は実施してよいと書く。
  - 要約には、未完成であることと止める地点を書く。
  - 欠けている情報は、影響と決める人を添えて一覧にする。決める人が資料から分からなければ「未定」と書く。

### 7. 読者の目で確かめる

- 要約だけを読んで、何の文書か、結論、読者がすることが分かる。
- 見出しと各段落の 1 文目だけを読んで、筋が通る。
- 作業メモ（除外の列挙、調べた経緯、訂正、会話への返答）が残っていない。
- 未定義語が残っていない。
- 読者の判断・行動を左右しない「未定」「未確認」を書いていない。
- [references/doc-types.md](references/doc-types.md) の該当する節の項目を、1 つずつ満たしている。
- 操作を書いた文書では、各操作に期待する結果があり、取り消せない操作やデータが失われる操作の直前に警告がある。
- 図と本文の要素名と順序が一致し、ASCII 図の縦の記号がずれていない。
- 量の目安を大きく超えた箇所がない。
- 手順書や分岐の多い文書は、会話の文脈を持たないサブエージェントに文書だけを渡し、全体像と自分が行う作業を説明させる。説明が意図とずれた箇所を直す。
