# 文書の種類ごとのルール

書く文書に該当する節だけを読む。SKILL.md の手順に加えて、各節のルールを守る。リポジトリに既存のテンプレートや規約がある場合は、構成と形式はそちらに従い、この節は内容の判断に使う。

「本文の順」に挙げた項目のうち、書く内容がないものは節を作らない。内容が「未定」だけの項目も節を作らず、未定の一覧に入れる。

## README

- 読者と場面: リポジトリを初めて開いた人。これは何か、自分に関係するか、どう始めるかを知りたい。
- 要約: 何をするものかを 1 文で書く。開発停止や非推奨など、通常と違う状態ならそれも書く。
- 本文の順: 最小の使用例と期待する出力 → セットアップ → 構成の全体図 → 詳しい文書へのリンク → 問い合わせ先・貢献方法。
- README は入口に留め、詳細は別の文書に分けてリンクする。コマンドはコピーしてそのまま動く形にする。
- 書かない: 開発の経緯、全 API の羅列、エージェント向けの細かな指示（`AGENTS.md` などに分ける）。

## 設計文書・RFC

- 読者と場面: レビュアーと将来の参照者。何を解決し何を解決しないか、なぜこの案か、自分のシステムに影響するかを知りたい。
- 要約: 何をどう変えるかと、読者に決めてほしいこと（承認、論点）を書く。
- 本文の順: 背景（現状と問題を 2〜3 文）→ 目標と非目標 → 設計（全体図を含む）→ 却下案 → 影響（依存先、運用負荷、セキュリティ、移行）→ 未決事項。
- 非目標には「目標にもなり得たが、今回は扱わないこと」を書く。「落ちないこと」のような否定形の目標は書かない。
- 却下案は、案と却下した理由を各 1 行で書く。検討の経緯は書かない。
- トレードオフがない変更は設計文書にせず、PR の説明に書く。
- 実装後の扱いは、その場所の方針に合わせる。実装に合わせて更新するか、決定時点の記録として残し、変更は新しい文書に書く。

## ADR

- 読者と場面: 将来の開発者。なぜこうなっているのか、変えてよいのかを知りたい。
- 構成: タイトル（決定を表す名詞句）、ステータス（提案・承認・廃止・置換先の ADR 番号）、日付、背景、決定、却下案、結果。
- 背景には、決定を迫った事実と制約だけを書き、結論を混ぜない。
- 決定は「〜する」と言い切る。
- 却下案は、案と却下した理由を各 1 行で書く。決め手がなかった場合は、そう書く。
- 結果には、得られるものと受け入れる代償の両方を書く。
- 1 つの ADR に 1 つの決定を書く。長さは 1〜2 ページまでにする。
- 承認済みの ADR は書き換えない。決定を変えるときは新しい ADR を作り、古い ADR のステータスを「置換: ADR-xxx」にする。

## 手順書・Runbook

- 読者と場面: 実際に操作する人。障害対応中は時間がなく、背景も知らない。
- 要約: 何のための手順か、いつ使うか、所要時間、影響（停止の有無と範囲）、必要な権限を書く。
- 本文の順: 前提条件（権限、ツールとバージョン、作業前の状態）→ 手順 → 完了の確認 → 失敗時の切り戻し → エスカレーション先。
- 手順は番号付きにし、1 ステップに 1 つの操作を書く。ステップ内は「目的 → 場所（ホスト、ディレクトリ、画面）→ 操作 → 期待する結果」の順にする。
- 期待する結果は、数値や文字列で判定できる形にする。「正常であることを確認する」とは書かない。
- コマンドは、コピーしてそのまま動く形にする。プロンプト記号 `$` を付けず、出力は別のコードブロックに分ける。置き換える値は大文字の名前にし、直後にその値の意味と取得方法を書く。
- 取り消せない操作の直前に、何が起きるか、取り消せるか、避ける方法（バックアップなど）を書く。注意書きは 1 文書に 1〜2 個までにする。
- 分岐は、分岐する操作の配下に入れ子で書く。
- 前のステップで得た値を覚えておくことを求めない。記録する場所を指定する。
- 日付・時刻にはタイムゾーンを付ける。移行作業では、移行元と移行先を明記する。
- 毎回同じコマンドを順に流すだけの手順なら、文書化に加えて自動化を提案する。

## 調査報告

- 読者と場面: 結果を受けて判断する人。結論は何で、どれだけ確かで、次に何をするかを知りたい。
- 要約: 結論、確度（確認済みか推測か）、読者に求める判断や次の行動を書く。
- 本文の順: 結論を支える根拠（ログ、コードの位置、計測値と出典）→ 影響範囲 → 未確認事項とその確かめ方 → 次の行動。
- 根拠には、結論を直接支える事実だけを書く。原因ではなかったものの計測値や、再現しなかった試行は書かない。
- 事実、推測、未確認を分けて書く。推測には根拠を添える。
- 結論や数値に付いている限定条件（期間、環境、件数）を落とさない。
- 次の行動には担当と期限を書く。決まっていなければ「未定」と書く。
- 原因の連鎖や関係する構成要素は、全体図で示す。
- 書かない: 調べた順序、否定された仮説、再現しなかった試行。

## 障害報告・ポストモーテム

- 読者と場面: 関係者と経営層。何が起き、影響はどれだけで、再発をどう防ぐかを知りたい。
- 要約: 「[サービス] が [期間] [影響]。原因は [トリガー]。」と、現在の状態（復旧済みか）を書く。
- 本文の順: 影響（停止時間、件数、利用者数）→ 原因（根本原因とトリガー）→ 復旧の方法 → 検知の方法 → 再発防止策 → 時系列。
- 再発防止策には、担当、期限、管理番号を書く。「改善する」「気をつける」のような、完了を判定できない対策は書かない。
- 時系列は最後に置き、時刻（タイムゾーン付き）と事実だけを書く。対応中の推測の移り変わりは書かない。
- 個人を責めず、仕組みと手順の問題として書く。

## PR

- 読者と場面: いまのレビュアーと、将来 `git blame` から辿ってくる人。何をなぜ変えたか、どこを見ればよいかを知りたい。
- タイトル: 何をどう変えたかが単独で分かる 1 文にする。「修正」「対応」だけにしない。言語や形式はプロジェクトの規約に従う。
- 本文の順: なぜ変えるか（問題と目的）→ 何を変えたか（diff からは読み取りにくい要点だけ）→ 確かめた方法（実行したコマンドと結果）→ レビューで見てほしい点 → 影響と残した課題。
- diff の言い換えを書かない。画面の変更には、変更前後のスクリーンショットを付ける。
- レビューで変更が入ったら、本文を最終的な変更に合わせて直す。
- 書かない: 作業の経緯、試して戻した変更。

## Issue

- 要約: 何が問題か、誰に何をしてほしいかを書く。バグなら、期待する動作と実際の動作を書く。
- 本文の順: 再現手順（環境、バージョン、操作、結果）→ 影響 → 分かっていることと分かっていないこと → 提案（あれば）→ 完了条件。
- 完了条件は、誰が見ても同じ判定になる形で書く。

## コミットメッセージ

- 件名: 何をするかを命令形で短く書く。英語なら 50 字程度にする。言語と形式（Conventional Commits など）はプロジェクトの規約に従う。
- 本文: 変更前の問題、変更後の状態、その方法を選んだ理由を書く。diff から分かることは書かない。
- 議論は URL だけで済ませず、要点を書く。
- 1 つのコミットには 1 つの論点を含める。

## Changelog・リリースノート

- 読者と場面: 利用者。更新すると何が変わり、何が壊れるかを知りたい。
- 新しい版を上に置き、版ごとに日付を書く。変更は追加、変更、非推奨、削除、修正、セキュリティなどに分ける。既存の形式があればそれに従う。
- 破壊的変更、非推奨、利用者が行う移行作業を、各版の最初に書く。
- コミットログをそのまま並べず、利用者から見た違いにまとめ直す。

## 社内向けの投稿（Slack、Wiki、メール）

- 1 行目: 何の連絡か（共有、依頼、判断の依頼）と結論を書く。依頼なら、誰に、何を、いつまでにしてほしいかを書く。
- 本文には、依頼や判断に必要な情報だけを書き、詳細は Wiki や Issue へリンクする。
- Slack への投稿は 1 画面に収める。Mermaid を表示できない場所では、ASCII 図にするか、図のある文書へリンクする。
- Wiki に書く手順や設計は、この文書の該当する種類のルールに従う。
