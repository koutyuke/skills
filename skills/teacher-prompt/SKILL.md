# Teacher Prompt

特定の技術 X について、「なぜそう書くのか」「X はどう考えるのか」まで教えるメンターとして Agent を振る舞わせるプロンプトを作る。成果物は `# Xを超絶丁寧に教えてくれる君.md` を見出しに持つ 1 つの Markdown ファイルである。

参考例は [assets/examples/rust-teacher.md](assets/examples/rust-teacher.md)(言語)と [assets/examples/effect-teacher.md](assets/examples/effect-teacher.md)(ライブラリ)にある。節の骨格と技術ごとの差し替え方は [references/section-map.md](references/section-map.md) にある。まず参考例を 1 つ読み、骨格を確認してから書く。

## 成果物の条件

出来上がったプロンプトに従う Agent が、次の回答をできる状態にする。

- **結論から始める。** 短い答え → 最小のコード例 → 動きの説明 → なぜそうなるか、の順で答える。
- **「なぜ？」を解く。** 構文の説明で終わらせず、X が何を防ぎ、何を実現しようとしているかを説明する。エラーは言い換えではなく、原因、X の意図、修正、避け方の順で説明する。
- **図で示す。** 型の変化、所有の移動、依存の関係、処理の流れ、状態遷移など、X で理解の鍵になる構造を ASCII 図で描く。図は概念の簡略図であると明示する。
- **比較する。** 似た概念の違いだけでなく、どの場面でどちらを選ぶかまで説明する。
- **「もう一歩踏み込むと」を添える。** 内部の仕組み、性能、設計思想、他技術との違いを、本題より短く紹介する。
- **「コラム」を添える。** 本題の理解につながる派生知識を、見出し `### コラム: ...` で短く書く。
- **初学者を壊さない。** 動き → なぜ → X らしい書き方 → 深い仕組み、の優先順位を守り、専門用語は初出で説明する。
- **自力で書けるようにする。** 答えを渡す Agent ではなく、エラーを自分で読み、型や構造から意味を推測できる状態を最終目標にする。

## 進める

### 1. 対象と読者を決める

- 技術名と版を確定する。版によって API や慣習が変わる技術では、学習対象の版を本文に明記させる。
- 学習者の前提知識を「知っているもの」と「前提にしないもの」に分ける。言語なら他言語の経験、ライブラリなら土台となる言語の習熟度を基準にする。
- 学習の場を確認する。実際に X を使っているリポジトリがあれば、その構成とプロンプトを対応付ける節を設ける。
- 保存先と文体を決める。プロジェクト内に置くなら、そのプロジェクトのドキュメント規約(配置、文体、正本の扱い)を先に読み、規約に居場所がなければ X を使っているパッケージの直下など、規約の対象外で見つけやすい場所を選ぶ。
- 仮定で安全に進められる場合は仮定を明示して進める。質問は成果物が大きく変わる点だけに絞る。

### 2. 調べる

- X の現在の API、推奨される書き方、版差を一次情報で確認する。ライブラリやフレームワークでは Context7 または公式ドキュメントを使い、記憶だけで API 名を書かない。
- リポジトリと結びつける場合は、実際のコードを読み、X の概念とファイル・シンボルの対応表を作る材料を集める。判断理由が ADR などに書かれているなら、その正本を参照させ、プロンプトへ同じ理由を書き写さない。
- 初学者がつまずく典型例を集める。コンパイルエラー、型エラー、実行時エラーのうち、X で最初に出会う種類を特定する。

### 3. 骨格を決める

- [references/section-map.md](references/section-map.md) の共通骨格を使う。すべての節を機械的に埋めず、X で意味を持たない節は落とし、X 固有の節を加える。
- 技術ごとに必ず決める項目を埋める。
  - メンタルモデルの柱(3〜8 個)。X の理解を支える中心概念。
  - エラーの種類と、最初に出会うエラーの読み方。
  - 比較リスト(15 項目以上)。
  - 図にする構造(2 種類以上)。
  - 学習用の近道(Rust の `unwrap()`、Effect の `runSync` のように、学習では許すが本番では注意する操作)。
  - 危険に見えるが宣言である機能(Rust の `unsafe`、Effect の `die` のように、「危険」で終わらせず意図を説明する対象)。
  - ツールチェーンのコマンドと、その意味。
  - エコシステム(外部パッケージ、隣接ツール、版の系統)。

### 4. 書く

- 見出しは `# Xを超絶丁寧に教えてくれる君.md` で始め、`## Role` から `## Final Goal` までの節で構成する。節名は参考例に合わせて英語、本文は日本語にする。
- 指示文は Agent への命令として簡潔に書く。メンターの回答例は `>` の引用で示し、学習者へ話す口調にする。
- 各節に、X 固有のコード例、図、または回答例を少なくとも 1 つ置く。一般論だけの節を作らない。
- コード例は単体で動く最小の形にし、変数名で意図を伝える。型や構造が鍵になる場面では、型注釈やコメント形式の型表示を添える。
- 間違い例は「これは動かない例である」と明記し、直後に修正版を置く。
- コラムは本文に 2 本以上書き、追加候補を箇条書きで残す。
- 「もう一歩踏み込むと」で扱う話題を箇条書きで挙げ、本題より長くしない旨を書く。
- 特定リポジトリと結びつける節では、概念と配置の対応表を置き、理由は正本の ID またはパスで参照させる。

### 5. 検証する

- プロンプト内のコード例を 1 つの検証用ファイルへ集め、対象の版で実際にコンパイル、型検査、または実行する。検証用ファイルはリポジトリ外の一時領域に作り、終わったら削除する。
- 間違い例が本当に失敗することを確認する。TypeScript なら `@ts-expect-error`、Rust なら `compile_fail` のような仕組みか、実際のエラー出力で確かめる。
- 本文中の API 名、コマンド、パス、版の記述を一次情報またはリポジトリと照合する。
- 保存先のプロジェクトに整形器やリンターの対象なら実行する。文体が規約と一致しているか確認する。
- 見出し、リスト、表、コードフェンスの構造を確認する。

### 6. 報告する

- 保存先、節の構成、参考例との差分、検証した内容と方法、未検証の事項、置いた仮定を分けて伝える。
- 検証で見つけた API の変更や版差があれば、プロンプト本文へ反映済みであることを明示する。

## 品質ゲート

完了前に確認し、不足があれば直す。

- 結論 → コード例 → 解説 → なぜ、の順が Response Style と Suggested Response Structure の両方に書かれているか。
- メンタルモデルの節に、X の中心概念が図付きで書かれているか。
- エラー説明の節に、X で最初に出会うエラーの実例と、6 段階の説明手順があるか。
- 比較リストが 15 項目以上あり、「どちらを選ぶか」まで説明させているか。
- 間違い例と修正版が対になっており、間違い例が実際に失敗することを確認したか。
- コラムが 2 本以上あり、`### コラム: ...` の形式か。
- 「もう一歩踏み込むと」の話題と、本題より長くしない旨があるか。
- Do Not Overcomplicate の優先順位と、初学者に最初から出さない話題が具体名で書かれているか。
- 学習用の近道と、危険に見える機能の扱いが節として書かれているか。
- コード例を実際に検証し、一時ファイルを削除したか。
- Final Goal が「答えを渡す Agent ではなくメンター」で締められているか。

## 例外

- 対象が非常に小さい(単一の関数やコマンド)場合は、骨格を縮めて Role、Response Style、Error Explanation、Comparisons、Final Goal だけにしてよい。その場合も「なぜ？」と図の要件は落とさない。
- 既存のプロンプトを更新する場合は、全面的に書き直さず、不足している節と検証されていないコード例だけを直す。
- 一次情報で API を確認できない場合は、該当箇所を推測で埋めず、本文に確認が必要な旨を残して報告する。
